在配置好的 LLGo 开发环境中运行检查。先测试实现相关行为的包。如果改动会影响程序运行，再执行链接后的程序或测试。[配置 LLGo 开发环境](/zh-CN/docs/llgo/contributing/development)

## 运行有针对性的本机检查

从编译器仓库根目录运行编译器测试包，并通过当前源码树的 LLGo 驱动运行标准库包测试。

```sh
go test ./cl
./dev/llgo.sh test ./test/std/runtime
```

第一条命令验证编译器行为，包括转换测试中对 LLVM IR 的断言。第二条命令用 LLGo 构建并执行仓库中的标准库运行时测试。定位失败原因时，可用 `-run` 选取特定测试。

| 改动范围 | 上游验证入口 |
| --- | --- |
| 从 Go 转换到 LLVM IR | `go test ./cl ./ssa` |
| 构建依赖图、链接或插桩 | 运行 `go test ./internal/build` 并选取相关测试 |
| 对外命令或选项行为 | `go test ./cmd/llgo` 和 `go test ./cmd/internal/compat` |
| 运行时源码或调用栈回溯 | 在 `runtime/` 模块中运行受影响的宿主机测试，并用 `./dev/llgo.sh test` 验证 `test/go/` 或 `test/std/` 下的相关包 |
| 某个标准库包 | 对比 `go test ./test/std/bytes` 和 `./dev/llgo.sh test ./test/std/bytes`，将示例路径换成受影响的包 |
| 特定版本的 Go 工具链 | `./dev/test_go_version.sh 1.24 ./test/std/bytes` |
| GOROOT 中的编译器测试用例 | 使用 `dev/test_goroot.sh`，并按 `test/goroot/README.md` 选取用例 |

根模块和 `runtime/` 分别有自己的 `go.mod`。例如，可用 `go -C runtime test ./internal/traceback` 运行调用栈回溯的宿主机测试。在仓库根目录执行 `go test ./...` 时，只会遍历根模块。

## 检查受影响的目标

WebAssembly、嵌入式镜像和调试会话各自需要相应的工具链和运行器。根据改动涉及的执行路径选取检查。

| 场景 | 上游检查 |
| --- | --- |
| WebAssembly 目标选择、Go 数据布局和原生调用边界 | 将目标工具链和运行器加入 `PATH`，再运行 `bash dev/test_wasm_target_profiles.sh` |
| WASI 线程和垃圾回收 | 使用 LLGo 指定版本的 Wasmer 运行器执行 `python3 dev/test_wasm_wasi_threads.py` |
| 在 Cortex-M 模拟器上进行嵌入式调试 | 按 README 准备 QEMU 和调试器依赖，再运行 `bash test/debug/embedded/runtest.sh` |
| 原生源码级调试 | 将当前源码树构建的 `llgo` 和受支持的 LLDB 加入 `PATH`，再运行 `bash test/debug/native/runtest.sh` |

记录结果时，请注明 Go 版本、宿主平台和编译目标，并区分编译、模拟器执行和实体设备执行。对于 Go 兼容性用例，使用上游的 `xfail.yaml` 记录已审查的预期失败，用 `notapplicable.yaml` 记录超出 LLGo 兼容范围的用例。[上游验证指南](https://github.com/xgo-dev/llgo/blob/52d17197e475f1c1f99d8472091defdfc63526ea/CONTRIBUTING.md#choose-tests-for-the-change) · [开发脚本](https://github.com/xgo-dev/llgo/blob/52d17197e475f1c1f99d8472091defdfc63526ea/dev/README.md)
