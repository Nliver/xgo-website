---
title: 类文件规范
description: 查阅 XGo 类文件的语法、类型生成、名称解析、框架注册及入口合成规则。
---

本文定义 XGo 类文件的语法和语义。

编译器将类文件转换为一个生成的类类型，以及一组生成的方法和用于衔接代码的辅助逻辑。

类文件分为两种。

- 普通类文件，即未在注册表中注册的 `.gox` 文件。
- 框架类文件，即类后缀已在类文件注册表中注册的文件。

## 术语

本文采用以下术语。

- 类后缀，用于查找框架的规范化类文件后缀，例如 `_app.gox` 和 `.gsh`。
- 类文件主名，去掉类后缀后的文件名。
- 类类型，编译器为类文件生成的命名类型。
- 字段声明块，唯一一处声明类字段的顶层 `var` 声明。
- 隐式入口，由顶层语句合成的函数。
- 项目类文件，表示项目级类的框架文件。
- 工作类文件，同一框架中表示非项目类的框架文件。
- 基类，由类文件元数据指定的嵌入框架类型。

## 文件分类

### 提取类后缀

从文件名本身提取类后缀。

文件名的最后一个扩展名为 `.gox` 以外的其他后缀时，类后缀取最后一个扩展名。

最后一个扩展名为 `.gox` 时，按以下规则确定类后缀。

- 若 `.gox` 前存在下划线，且最后一个下划线并非文件名的首字符，则取该下划线开始的后缀。
- 其他情况下取 `.gox`。

例如：

- `Rect.gox` 的类后缀为 `.gox`。
- `main_app.gox` 的类后缀为 `_app.gox`。
- `main.gsh` 的类后缀为 `.gsh`。

### 源文件种类

满足下列任一条件的源文件视为类文件。

- 类文件注册表识别出该文件名。
- 文件名以 `.gox` 结尾，且注册表没有识别出其规范化类后缀。

满足第二项时，该文件为普通类文件。满足第一项时，该文件为框架类文件。

### 项目文件与工作文件

注册表识别出的每个类后缀只归属一项框架注册。

对于已经识别的文件，若框架的注册信息将 `(类后缀, 文件名)` 标记为项目文件，该文件就是项目类文件。其他已识别的文件为工作类文件。

- 当项目后缀与工作类后缀不同时，规范化类后缀等于项目后缀的每个文件都是项目文件。
- 当两类后缀相同时，只有文件名为 `main` 加上该后缀的文件属于项目文件，其他采用相同后缀的文件都属于工作文件。

例如：

- 两类后缀都是 `_case.gox` 时，`main_case.gox` 是项目文件，`foo_case.gox` 是工作文件。
- 项目后缀为 `_app.gox`、工作类后缀为 `_cmd.gox` 时，`demo_app.gox` 是项目文件，`list_cmd.gox` 是工作文件。

## 源码形式

### 包子句

类文件可以省略包子句，此时按声明了 `package main` 的方式编译。

### 导入

导入声明遵循普通 XGo 源文件的规则。

- 导入声明必须位于所有其他声明和顶层语句之前。
- 源码中的普通导入经过编译转换后仍是普通的包导入。

### 顶层结构

忽略注释后，类文件具有如下顶层结构。

```text
Classfile = [ PackageClause ] { ImportDecl } { ClassDecl } [ TopLevelStmtList ] .
ClassDecl = ConstDecl | TypeDecl | VarDecl | FuncDecl .
TopLevelStmtList = StatementList .
```

可选的 `TopLevelStmtList` 必须是文件中最后一个顶层结构。遇到第一条顶层语句后，解析器按普通函数体的语句列表规则处理余下的文件，作为隐式入口的函数体。

因此，函数体中有效的语句结构会成为隐式入口的一部分。例如 `var x = 1` 这样的局部声明语句会留在入口方法内部。

### 字段声明块

在类文件转换过程中，最多有一处顶层 `var` 声明会被解释为字段声明块。它必须符合以下条件。

- 是文件声明列表中的顶层 `var` 声明。
- 位于该声明之前的所有顶层声明（如有）均为 `import`、`const` 或 `type` 声明。
- 是第一处符合这些条件的顶层 `var` 声明。

该块声明生成的类类型的字段。其他 `var` 声明遵循普通变量声明规则。出现在隐式入口开始前的声明定义包变量，出现在隐式入口开始后的声明是入口方法内部的局部声明语句。

本规范的嵌入字段语法只适用于字段声明块。

### 字段声明语法

字段声明块中的每个声明项都采用下列形式之一。

```text
FieldSpec      = EmbeddedField [ Tag ]
               | IdentifierList [ Type ] [ "=" ExpressionList ] [ Tag ] .
EmbeddedField  = [ "*" ] TypeName
               | [ "*" ] PackageName "." identifier .
Tag            = string_lit .
```

仅在字段声明块中适用一条特殊规则。若声明项恰好包含一个标识符，没有显式类型和初始化表达式，则它声明类型名为该标识符的嵌入字段。这是 `IdentifierList` 唯一可以同时省略 `Type` 和 `=` 初始化表达式的情况。

其他 `FieldSpec` 遵循普通 `var` 声明的有效性规则，必须提供 `Type` 或 `=` 初始化表达式中的至少一项。

例如：

```xgo
var (
  Width, Height int
  *bytes.Buffer "buffer"
  BaseClass
)
```

在字段声明块中：

- 嵌入字段不得使用初始化表达式。
- 普通字段和嵌入字段都可以使用标签。
- 引号包围的标签按源码原样接受。若字符串没有显式的标签键，生成的 Go 标签为 `_:"..."`。

## 生成类类型

### 类型命名

编译器为每个类文件生成一个命名类类型。初始类型名来自类文件主名，按以下规则规范化。

- 删除 `:` 和 `#`。
- 将 `-` 和 `.` 替换为 `_`。

例如：

- `Rect.gox` 生成初始类型名 `Rect`。
- `get_p_#id_app.gox` 的类文件主名为 `get_p_#id`，规范化后的类型名为 `get_p_id`。

框架元数据可进一步修改类型名。

- 主名为 `main` 的项目文件，或没有显式项目文件的框架，默认使用项目基类名作为类类型名。去掉基类名开头的 `*`。
- 非空的工作类 `-prefix=` 会加到规范化后的工作类文件主名之前。
- 若前两条均不适用，且类类型名与以下任一保留名称相同，则在名称前加下划线。`init`、`main`、`go`、`goto`、`type`、`var`、`import`、`package`、`interface`、`struct`、`const`、`func`、`map`、`chan`、`for`、`if`、`else`、`switch`、`case`、`select`、`defer`、`range`、`return`、`break`、`continue`、`fallthrough`、`default`。

所有规范化完成后，生成的类类型必须在包中唯一。

### 底层类型

每个类类型的底层类型都是结构体。

普通类文件的结构体字段由用户在字段声明块中定义，按源码顺序排列。

对于框架类文件，框架添加的字段排在用户字段之前。

### 框架添加的字段

框架按以下顺序插入字段。

- 对于项目类文件，嵌入项目基类。
- 对于项目类文件，按工作类声明顺序和源文件路径的字典顺序插入由 `-embed` 指定的工作类嵌入字段。
- 对于工作类文件，嵌入工作基类。
- 对于工作类文件，若项目类类型存在且对应的字段名与现有字段不冲突，则嵌入指向项目类类型的指针。

字段声明块中的用户字段添加到所有框架字段之后。同一类类型中若存在两个同名的生成字段，编译失败。

## 函数和方法

### 隐式接收者改写

类文件中，每个没有显式接收者的顶层函数声明都会改写为生成的类类型上的方法。编译器注入名为 `this`、类型为 `*T` 的接收者，其中 `T` 为生成的类类型。

该规则适用于普通函数声明，包括名为 `init` 的函数。类文件中的 `func init()` 声明名为 `init` 的方法，与包初始化函数无关。

同理，类文件中的 `func main()` 声明名为 `main` 的方法，不影响包级入口的选择。

### 显式接收者声明

已经包含显式接收者的顶层函数声明保持原样。

### 静态方法声明

类文件解析器还接受下面这种仅适用于类文件的 `FuncDecl`。

```text
StaticMethodDecl = "func" "." identifier Signature [ FunctionBody ] .
```

该形式声明与生成的类类型关联的静态方法，后续转换遵循 XGo 的普通静态方法规则。

### 隐式入口

顶层语句放入最初参数列表为空的合成函数，称为隐式入口。类文件转换时，入口按以下规则命名。

- 项目类文件使用 `MainEntry`。
- 其他类文件使用 `Main`。

框架类文件没有显式顶层语句时，编译器仍会合成同名的空入口。框架入口方法因此总是存在。

普通类文件没有顶层语句时，编译器不合成 `Main`。

### 向基类入口转发

若编译器为框架类文件合成 `Main` 或 `MainEntry`，且嵌入的基类声明了同名方法，合成的方法会沿用基类方法的参数和结果列表，仅将基类接收者替换为类文件接收者 `*T`。

在执行用户编写的顶层语句前，生成的方法体会先将传入的实参转发给嵌入的基类方法。

### 合成入口方法的执行顺序

合成的 `Main` 或 `MainEntry` 固定按以下顺序执行。

1. 若生成的类类型直接定义了 `XGo_Init`，调用 `this.XGo_Init()`。
2. 若嵌入的基类有同名方法，调用该方法。
3. 执行隐式入口包装的用户顶层语句。

若沿用的方法签名包含结果参数，转换后的方法体按该签名对应的普通 Go 控制流规则检查。

## 字段初始化

### 生成 XGo_Init

若字段声明块中至少一个字段带有初始化表达式，编译器会生成以下方法。

```xgo
func (this *T) XGo_Init() *T
```

生成的方法按字段声明顺序执行所有字段的初始化赋值，然后返回 `this`。若字段声明块中没有初始化表达式，就不会生成 `XGo_Init`。

### XGo_Init 的调用条件

字段初始化表达式不会附在结构体类型本身。以下操作都不会自动执行字段初始化。

- `new(T)`
- `&T{...}`
- `T{...}`
- 调用用户声明的 `Main` 方法
- 调用用户声明的 `MainEntry` 方法
- 调用前述合成的入口方法之外的普通方法

如果类类型有 `XGo_Init`，但没有合成入口调用它，该方法不会自动执行。

## 类方法内部的名称解析

类方法体内，未限定标识符的解析规则不同于包级 XGo 代码。解析按以下顺序进行。

1. 当前词法作用域的局部声明。
2. `this` 的成员。
3. 当前包内的包作用域声明。
4. 普通 XGo 函数别名改写。
5. 在框架的包查找集合中搜索隐式可用的导出标识符。
6. 全域作用域中的预声明标识符。

还有两条规则。

- 标识符作为选择表达式的左侧时，解析还考虑源码中导入的包名，以及模块元数据中自动导入的包名。
- 若同一个隐式框架导出名称出现在多个框架查找包中，编译会因名称冲突失败。

查找隐式框架包的导出成员时，适用 XGo 普通包成员别名规则。例如，导出的函数可以通过小写别名访问。

注入的 `this` 为普通方法接收者标识符，可以显式引用。

## 框架注册元数据

### 元数据来源

类文件注册表由三个来源构成。

- 工具链定义的内置框架注册。
- 当前模块的 `gox.mod`。
- `go.mod` 中带 `//xgo:class` 注释的 `require` 行导入的依赖注册。

### 内置注册

以下两项是工具链定义的全部内置框架注册。

```text
project .gsh App github.com/qiniu/x/gsh math

project _test.gox App github.com/goplus/xgo/test testing
class _test.gox Case
```

内置注册无需模块声明即可生效。文件分类、编译转换及包组装均按读取自模块元数据的注册方式处理这些内置注册。

### 识别类文件指令

类文件加载器识别以下模块指令。

```text
ProjectDirective = "project" [ ProjectExt ExportedName ] PackagePath { PackagePath } .
ClassDirective   = "class" { ClassDirectiveFlag } WorkExt ExportedName [ ExportedName ] .
ImportDirective  = "import" [ ImportName ] PackagePath .
ClassDirectiveFlag = "-embed" | "-prefix=" string_without_space .
```

每个 `class` 或 `import` 指令归属前面最近的 `project`。一个项目组由一条 `project` 指令和所属的全部 `class`、`import` 指令构成。

`project` 的第一个包路径用于解析该项目组引用的基类符号。后续包用于查找隐式框架导出名称，解析基类符号时不会搜索这些包。

### 后缀格式与规范化

`project` 和 `class` 指令支持两种后缀记号。

- `_[class].gox`
- `.[class]`

两种形式各自独立，均由类文件机制支持。新建框架注册推荐采用 `_[class].gox`。该建议不限制前述内置注册。

本规范定义上述两种形式的文件分类和编译语义。辅助工具可自行决定是否自动识别任意非 `.gox` 后缀。

`project` 和 `class` 的后缀标记前可以写 `*`。对于 `project`，标记也可带 `main` 前缀。加载器去掉这些前缀，只保留用于匹配的类后缀。

例如：

- `*_cmd.gox` 规范化为 `_cmd.gox`。
- `main_app.gox` 规范化为 `_app.gox`。

### 类元数据的含义

对于每条 `project` 指令：

- 提供了 `ProjectExt` 和 `ExportedName` 时，该指令定义项目文件类型及项目基类名称。
- 省略这两个参数时，项目文件类型与项目基类均未设置。该指令仍定义包查找集合，以及后续 `class` 和 `import` 所归属的项目组。
- 指定项目基类时，从第一个包路径对应的包中解析该符号。
- 基类名前可以加 `*`，此时生成的项目类嵌入的是指向命名基类型的指针。

对于每条 `class` 指令：

- 导出符号指定工作基类。
- 可选的最后一个导出符号指定工作类原型类型。
- 若一个项目组声明了多种工作类，每种都必须声明原型类型。
- `-prefix=` 为生成的所有对应工作类类型名添加指定前缀。
- `-embed` 使项目类为该种工作类生成的每个实例嵌入一个字段。

对于每条 `import` 指令：

- 导入的包名自动对类文件可用。
- 未显式给出导入时使用的名称时，采用包声明中的包名。
- 同一项目组中多条 `import` 解析为相同的自动导入名时，最后一条生效。

## 组装项目类与工作类

项目后缀以 `test.gox` 结尾的框架注册归类为测试框架注册。其他注册均为非测试框架注册。

### 合成默认项目类

对于同一项框架注册，一个包最多只能包含一个显式项目类文件。若该包包含多个属于同一注册的显式项目类文件，编译失败。

如果框架注册提供了项目基类，而包中没有该框架的显式项目文件，编译器仍会合成一个默认项目类类型。合成的类没有自己的源文件，类型名遵循前述项目类型命名规则。

### 为项目 Main 组装工作类实例

对于每个提供项目基类的非测试框架注册，编译器在项目类类型上生成 `Main` 方法。项目基类因此也必须提供 `Main` 方法。生成的项目方法构造工作类实例，并将它们转发给嵌入的项目基类 `Main` 方法。

分组规则如下。

- 框架只有一种工作类，且 `Main` 的相应参数为可变参数时，该类对应的所有工作文件都作为可变实参传入。
- 其他情况下，工作文件会按声明的原型类型分组，按 `Main` 的参数顺序以切片传入。

项目 `Main` 会为包内每个工作文件创建一个新实例。工作类声明含有 `-embed` 时，在调用项目基类的 `Main` 前，新实例也会被赋值给项目实例上相应的嵌入字段。

## 合成辅助方法

如果声明的工作类原型要求特定辅助方法，编译器可以为工作类合成这些方法。

### Classfname

若工作类原型包含名为 `Classfname` 的方法，编译器会生成如下方法，返回类文件主名。

```xgo
func (this *T) Classfname() string
```

例如：

- `hello_tool.gox` 返回 `hello`。
- `get_p_#id_app.gox` 返回 `get_p_#id`。

### Classclone

若工作类原型包含 `Classclone` 方法，编译器会生成一个同名的浅复制方法。除接收者外，方法没有其他参数，结果列表沿用原型中 `Classclone` 的声明。

生成的实现将 `*this` 按值复制到临时变量，并返回该临时值的地址。

## 合成包级 main

编译名为 `main` 的包时，编译器先检查是否已存在显式的包级 `main` 函数。若存在，就不会根据类合成包级 `main`。

若不存在，编译器按以下规则选择类入口。

1. 仅考虑非测试框架注册。
2. 优先选择唯一一个显式项目文件带有隐式入口的框架项目组。
3. 若没有这样的项目组，则选择剩余项目组中的唯一一项，也包括只有合成默认项目类的项目组。
4. 若未选中项目组，且恰好有一个普通类文件带有隐式入口，则选中该普通类文件。

若选中了类类型 `T`，编译器生成以下入口。

```xgo
func main() { new(T).Main() }
```

未选中类类型时，编译器生成空的 `main` 函数，但可以在编译器配置中禁用自动生成。

## 兼容性

工具链也接受以下历史别名。

- `gop.mod` 是 `gox.mod` 的旧称。只有没有 `gox.mod` 时才会读取 `gop.mod`。
- 依赖 `go.mod` 的 `require` 行可以使用 `//gop:class` 作为 `//xgo:class` 的历史别名。

## 与普通结构体及包语义的关系

转换后的类类型是普通的命名结构体类型，其方法会变为普通 Go 方法或静态方法的辅助实现。因此：

- 转换后的类类型的复合字面量遵循普通结构体字面量规则。
- 同一包中声明的普通包变量、常量、类型和显式方法遵循普通包语义。
- 普通包变量的初始化顺序保持原样。

类文件机制只在源码层增加了转换规则，运行时仍采用转换后的 Go 代码所提供的对象模型。
