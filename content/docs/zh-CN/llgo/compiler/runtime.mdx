LLGo 提供自己的运行时。编译器按照该运行时的调用约定和数据布局，转换启动 goroutine、分配对象、调用闭包等操作。Go 源码兼容性让包可以继续通过熟悉的 Go API 执行这些操作。与原生库在二进制层面交互时，LLGo 使用目标平台的 C 应用二进制接口（ABI）。[Go 支持与运行时](https://github.com/xgo-dev/llgo/blob/v1.0.10/README.md#go-support)

## Goroutine 与内存

在原生目标上，每个 goroutine 运行在一个操作系统线程上，并使用大小固定的线程栈。同步调用 C 函数时，会继续使用同一线程栈并保留 goroutine 的上下文。如果 C 在同一线程回调 Go，回调将复用该上下文。外部线程进入 Go 时，运行时可以接管该线程。线程归属会影响垃圾回收和运行时检查。默认的本机回收器是保守式的 Boehm–Demers–Weiser 回收器（BDWGC），会将看起来可能是堆指针的值视为潜在引用。[原生调用边界](https://github.com/xgo-dev/llgo/blob/v1.0.10/runtime/NATIVE_CALLS.md) · [本机运行时](https://github.com/xgo-dev/llgo/blob/v1.0.10/README.md#runtime)

由宿主运行的 WebAssembly 有独立的调度与垃圾回收规则。Emscripten 构建默认使用一个 worker，也可以启用多个 worker，每个 goroutine 都固定在分配给它的 worker 上。Wasmer WASI 的 pthread 后端为每个 goroutine 分配一个 pthread，回收时可以暂停参与线程，在线性内存中执行串行回收。在这个后端中，线程如果阻塞在未插桩的 C 代码里，可能会推迟垃圾回收。如果等待线程暂停超时，回收器会恢复已暂停的线程并跳过本轮回收。裸机目标使用源自 TinyGo 的保守式标记清除回收器。使用 `nogc` 构建标签可以关闭垃圾回收。[Wasm 目标配置](https://github.com/xgo-dev/llgo/blob/v1.0.10/doc/wasm-proposal.md) · [WASI 多线程垃圾回收](https://github.com/xgo-dev/llgo/blob/v1.0.10/doc/wasm-threaded-gc.md) · [本机和裸机运行时](https://github.com/xgo-dev/llgo/blob/v1.0.10/README.md#runtime)

Wasm 中的 goroutine 栈大小固定。`-goroutine-stack-size=2MB` 会设置 goroutine 栈和对应 Asyncify 缓冲区的大小。该缓冲区在调用挂起时保存栈状态。主 goroutine 的栈大小单独设置。由 JavaScript 宿主运行的构建会检查栈边界，栈溢出时中止程序。[Wasm 栈大小](https://github.com/xgo-dev/llgo/blob/v1.0.10/README.md#standard-libraries)

## 函数值与闭包

LLGo 的函数值包含代码指针和环境指针。普通函数的环境指针为 nil。捕获变量的闭包和绑定了接收者的方法将所需的值保存在环境中。环境属于底层调用约定的一部分，所以闭包与具有相同参数和返回值的普通函数仍然拥有相同的 Go 函数类型。

LLVM 目标决定如何传递环境。符合条件的原生目标通过 LLVM 的 `nest` 或 `swiftself` 属性选择一个隐藏寄存器。对需要环境的入口，Wasm 使用显式参数。反射通过目标平台对应的 libffi 适配器调用这类入口。如果外部 C API 接收函数指针和上下文参数，请直接传入回调函数，通过上下文参数传递状态。[闭包 ABI](https://github.com/xgo-dev/llgo/blob/v1.0.10/doc/closure.md) · [原生回调](https://github.com/xgo-dev/llgo/blob/v1.0.10/README.md#windows-api)

## 复用 Go 运行时源码

应用会使用一个 GOROOT，也就是 Go 工具链和标准库所在的目录。LLGo 复用其中经过审查的例程，包括 UTF-8 编解码和复数除法。加载包时，LLGo 通过源码覆盖引入所选实现，保留其 Go 源码的位置，并将源码内容纳入构建缓存的指纹。调度、栈切换、垃圾回收和类型元数据仍遵循 LLGo 的运行时约定。依赖 Go 内部 ABI 的代码，例如运行时汇编，其兼容性也受这些约定影响。[复用 GOROOT 的运行时源码](https://github.com/xgo-dev/llgo/blob/v1.0.10/doc/runtime-source-reuse.md)

在配置好的 LLGo 源码目录中，可以生成一份运行时源码归属报告。

```sh
go run ./dev/runtimeaudit -goos=linux -goarch=amd64 -o=runtime-linux.json
```

报告记录所选的 Go 版本、平台和构建标签，并标明运行时声明的来源、编译器引用的声明，以及哪些条目绑定到外部实现。该清单用于确认声明的归属。通过目标平台的编译和运行测试，可以继续验证 ABI 和实际行为。[运行时源码归属审计](https://github.com/xgo-dev/llgo/blob/v1.0.10/doc/runtime-source-reuse.md#ownership-and-upgrade-audit)
