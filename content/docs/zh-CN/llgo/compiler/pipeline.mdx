LLGo 从 Go 模块与包的依赖图开始构建。驱动程序确定所用的 Go 工具链和目标平台，选择源码文件，应用源码覆盖和运行时实现替换，再为选中的包构建带类型信息的表示。后续各阶段将这一表示转换为目标平台的代码。

| 阶段 | LLGo 的处理 |
| --- | --- |
| 加载包 | `internal/build` 中的驱动程序根据 Go 环境、模块依赖图和构建约束选择包。编译时所见的源码包含 LLGo 针对目标平台提供的运行时代码和所选 GOROOT 中的源码。 |
| 构建 Go SSA | 前端构建静态单赋值形式（SSA），其中每个计算结果只有一个定义。前端使用 Go 类型信息和选中的函数体，包括泛型实例化后的代码。符合条件的构建可以从缓存中恢复已校验的依赖数据。 |
| 分析生命周期 | 前端判断哪些引用可能在一次函数调用或循环迭代结束后继续存活。后续转换使用这一结果为局部变量、闭包环境、装箱的接口值等选择存储位置。 |
| 转换为 LLVM IR | `cl` 包负责转换 Go 包和函数。`ssa` 包为 Go 操作及对应的运行时调用生成 LLVM 中间表示（IR）。驱动程序也会执行目标相关的转换，例如按照 C ABI 生成调用。 |
| 生成与链接 | 驱动程序选择 LLVM 优化流程并生成目标文件或供链接时优化用的位码，再链接各包的产物和原生输入文件。最终处理阶段可以根据链接产物中的地址生成运行时函数及源码行号元数据。 |

## 逃逸分析如何选择存储位置

对变量取地址会产生编译器需要跟踪的引用。将引用传给编译器能够确定的函数时，变量仍有可能存放在栈上。例如，辅助函数将收到的指针原样返回时，LLGo 会跟踪调用方如何使用该指针。如果指针被存入生命周期更长的状态，原对象可能需要放到堆上。对于可确定的调用，编译器使用摘要来描述被调用函数如何保留、返回或修改值。对于一组相互递归的函数，编译器会一起分析，直至各函数的摘要稳定。无法确定安全的生命周期时，分析会保留保守的存储决策。

后端还会考虑对象大小、对齐、栈空间预算和垃圾回收器的要求。容量在运行时确定的切片可以在请求较小时使用调用方的缓冲区，超过容量时再从堆分配。对于显式登记垃圾回收根的目标，编译器会跟踪栈对象中的托管指针。即使借用该对象的被调用函数修改这些字段，回收器也能找到相应的指针。LLGo 完成源码级转换后，LLVM 还可以进一步优化内存分配。[逃逸分析设计](https://github.com/xgo-dev/llgo/blob/v1.0.10/doc/escape-analysis.md)

## 查看分配计划

在 Go 包目录中执行以下命令。最后一条命令接收该目录下的一个 Go 源文件。

```sh
llgo build -gcflags=-m=2 .
llgo build -gcflags=all=-m=2 .
llgo tool compile -m=2 file.go
```

第一条命令报告命令行指定包的分配决策，第二条也包含依赖包。第三条命令检查指定源码并生成中间表示，跳过链接。`-m=2` 会附上每项决策的原因。可留意 `stack`、`stack-buffer`、`borrowed` 和 `heap`。栈缓冲区可以在容量不足时改用堆分配，借用视图则引用已有存储。该报告反映的是 LLVM 优化前的前端计划。[分配诊断](https://github.com/xgo-dev/llgo/blob/v1.0.10/doc/escape-analysis.md#packages-caches-and-diagnostics) · [命令行兼容性](https://github.com/xgo-dev/llgo/blob/v1.0.10/doc/command-line/compatibility.md)

## 跨构建复用分析结果

开启构建缓存后，可以在受支持的构建中设置 `LLGO_ESCAPE_CACHE=1`，持久化前端分析结果。LLGo 根据对应的归档及其输入校验依赖分析数据，包括源码所用的工具链、目标数据布局，以及该包在编译时所见源码的变化。匹配的依赖可以提供已校验的导出类型信息和调用效果摘要，省去重建全部 SSA 函数体。缓存未命中，或内联和泛型实例化需要函数体时，LLGo 仍会加载源码。依赖完整程序才能作出的决策，例如选择启用哪些 Wasm 反射功能，会使用以完整构建为键的独立缓存项。[前端缓存](https://github.com/xgo-dev/llgo/blob/v1.0.10/doc/escape-analysis.md#packages-caches-and-diagnostics)
