## 什么是类框架？

**类框架**将领域知识抽象为可复用的应用骨架，其在 XGo 中的地位类似于 Go 中的 `interface`。

XGo 提倡**特定领域友好（SDF）**。框架作者用普通 Go 编写一次应用骨架，开发者再用轻量的 XGo 源文件填写领域逻辑。这些文件称为**类文件**，由 XGo 编译器自动连接到框架。

类框架包含两个角色。

- **项目类**是应用的根，每个项目恰好有一个实例。
- **工作类**描述组成应用的工作单元。框架可以定义多种工作类，项目通常包含多个工作类实例。

---

## 类文件

**类文件**是隐式定义类的 XGo 源文件。以 `Rect.gox` 为例。

```xgo
var (
    Width, Height int
)

func Area() int {
    return Width * Height
}
```

这个类文件等价于以下 Go 代码。

```go
type Rect struct {
    Width, Height int
}

func (this *Rect) Area() int {
    return this.Width * this.Height
}
```

开发者可以沿用熟悉的顺序编程写法定义新类型。对初学者来说，变量和函数仍采用普通声明语法，无需另写 `type` 声明或接收者。

## gox.mod 文件

每个类框架都提供 `gox.mod`，供 XGo 编译器识别类文件。指令的格式如下。

```text
project <filePattern> <BaseType> <importPath> [extraImports...]
class   [flags] <filePattern> <BaseType> [ProtocolType]
```

- `project` 指令注册项目类文件的匹配模式与基类型。
- `class` 指令注册工作类文件的匹配模式，可重复声明。框架定义多种工作类时，每条 `class` 指令需要提供 `ProtocolType` 参数。编译器通过这个接口将实例传给模板接收者方法中对应的参数。

| 选项 | 作用 |
| --- | --- |
| `-embed` | 在项目类的结构体中为每个工作类实例声明具名字段 |
| `-prefix=<P>` | 为此种工作类生成的每个类型名加上前缀 `P` |

### 类文件匹配模式

`gox.mod` 中的 `<filePattern>` 必须使用框架专有后缀，可以是 `*.spx`、`*.yap` 等自定义后缀，也可以是 `*_<class>.gox` 形式，例如 `*_script.gox`。普通 `*.gox` 属于共享后缀，同一项目可同时使用多个类框架。专有后缀让每个匹配的文件都有唯一的归属。

框架有多种工作类时，`ProtocolType` 接口标识对应的实例种类。编译器据此把实例放入模板接收者方法中相应的参数。

## 编译器生成的代码

XGo 编译器根据 `gox.mod` 声明和用户的类文件执行以下转换。

### 1. 生成结构体类型

项目类文件生成一个结构体并嵌入声明的 `BaseType`。每个工作类文件也生成一个结构体，其中嵌入该类的 `BaseType`，以及指向项目类实例的指针。使用 `-embed` 后，项目结构体还会为每个工作类实例生成具名字段。

### 2. 生成入口方法

**项目类文件**中的顶层语句编译到 `MainEntry()` 中。每个**工作类文件**中的顶层语句编译到 `Main()` 中。

如果基类型也实现入口方法，编译器会在执行用户代码前插入对基类型方法的调用。`ProtocolType` 接口负责描述预期的 `Main` 签名，供编译器生成正确的方法原型。

### 3. 合成项目的 Main 方法

编译器为项目类合成 `Main`，由它依次完成以下操作。

1. 创建所有工作类实例。
2. 初始化 `-embed` 生成的字段（如有）。
3. 调用框架的**模板接收者方法**，传入项目实例和所有工作类实例。

### 4. 生成包级入口函数

```go
func main() {
    new(ProjectClass).Main()
}
```

## 模板接收者方法

框架作者编写[模板接收者方法](/zh-CN/docs/reference/template-receiver-method)，在编译器组装完实例后接管执行。方法名采用 `XGot_<BaseType>_Main` 形式，早期版本也使用 `Gopt_<BaseType>_Main`。

方法签名描述框架的结构约定。

```go
// Single work class kind — variadic
func XGot_Game_Main(app Gamer, sprites ...Sprite)

// Multiple work class kinds — one typed slice per kind
func Gopt_MCPApp_Main(app iAppProto, resources []ResourceProto, tools []ToolProto, prompts []PromptProto)
```

编译器从签名获知工作类的种类数量和调用时的分组方式。框架通过这个方法建立运行环境、加载资源，并调用各个工作类的 `Main` 等方法。

## 框架示例

### SPX 2D 游戏引擎

`github.com/goplus/spx`

SPX 是 XGo 生态中最早的类框架，为 STEM 教育而设计。

#### gox.mod

```text
xgo 1.7

project main.spx Game github.com/goplus/spx/v2 math

class -embed *.spx SpriteImpl
```

- `main.spx` 是项目类文件，其类型自动嵌入 `spx.Game`。`main.spx` 中的顶层代码成为 `MainEntry` 的方法体。
- 其余 `*.spx` 文件是工作类文件，其类型各自嵌入 `spx.SpriteImpl`。顶层代码成为 `Main` 的方法体。`-embed` 让项目类为每个工作类实例生成具名字段。

#### 项目示例

一个飞行射击示例可以使用以下文件结构。

```text
main.spx        // game loop and setup
Bullet.spx      // bullet behaviour
Enemy.spx       // enemy behaviour
MyAircraft.spx  // player behaviour
```

#### 生成的 Go 代码

```xgo
// From main.spx — project class

type Game struct {
    spx.Game           // embedded base type
    Bullet     *Bullet // auto-generated by -embed
    Enemy      *Enemy
    MyAircraft *MyAircraft
    ... // user defined members in main.spx
}

func (this *Game) MainEntry() {
    ... // user code from main.spx
}

// Synthesized by the XGo compiler:
func (this *Game) Main() {
    bullet     := new(Bullet)
    enemy      := new(Enemy)
    myAircraft := new(MyAircraft)
    // initialise -embed fields
    this.Bullet     = bullet
    this.Enemy      = enemy
    this.MyAircraft = myAircraft
    // call the Template Recv Method
    spx.XGot_Game_Main(this, bullet, enemy, myAircraft)
}

// From Bullet.spx — work class

type Bullet struct {
    spx.SpriteImpl // embedded base type
    *Game          // pointer back to project instance
    ...            // user defined members in Bullet.spx
}

func (this *Bullet) Main() {
    ... // user code from Bullet.spx
}

// Enemy and MyAircraft follow the same pattern.

// Global entry point

func main() {
    new(Game).Main()
}
```

#### 模板接收者方法

```go
func XGot_Game_Main(game Gamer, sprites ...Sprite)
```

`*Game` 满足 `Gamer` 接口，每个工作类满足 `Sprite` 接口。引擎加载各精灵的资源，并调用其 `Main` 运行行为循环。

### cobra 命令行工具框架

`github.com/goplus/cobra`

#### gox.mod

```text
xgo 1.7

project *_app.gox App github.com/goplus/cobra/xcmd

class -prefix=Cmd_ *_cmd.gox Command
```

- `*_app.gox` 匹配项目类文件，其类型嵌入 `xcmd.App`。
- `*_cmd.gox` 匹配工作类文件，其类型各自嵌入 `xcmd.Command`。`-prefix=Cmd_` 为每个生成的类型加上 `Cmd_` 前缀。例如 `run_cmd.gox` 生成 `Cmd_run` 类型，避免 `run` 与常见标识符重名。

#### 项目示例

```text
myapp_app.gox   // application entry
run_cmd.gox     // "run" subcommand
build_cmd.gox   // "build" subcommand
```

#### 自定义 Main 签名

基类型 `xcmd.Command` 实现 `iCommandProto`。

```go
type iCommandProto interface {
    ...
    Main(fname string)
}
```

该接口告诉编译器每个工作类的 `Main` 都须接受一个 `string` 参数。因 `xcmd.Command` 本身也实现 `Main`，编译器会先插入对基类型方法的调用。

```go
type Cmd_run struct {
    xcmd.Command
    *xcmd.App
}

func (this *Cmd_run) Main(_xgo_arg0 string) {
    this.Command.Main(_xgo_arg0) // base class call, auto-inserted by compiler
    ...                          // user code from run_cmd.gox
}
```

项目类也适用这一机制。框架可以通过协议接口自定义 `MainEntry` 的签名，编译器会在生成的方法中合成对基类型方法的调用。

#### 模板接收者方法

```go
func XGot_App_Main(app iAppProto, cmds ...iCommandProto)
```

项目类满足 `iAppProto`，每个 `Cmd_*` 工作类满足 `iCommandProto`。框架将命令注册到底层 `cobra.Command`，并启动命令行应用。

### YAP Web 框架

`github.com/goplus/yap`

YAP 通过文件名定义路由。`get.yap` 处理 `GET /`，`get_p_#id.yap` 处理 `GET /p/:id`。最简单的 Web 服务器只要一个文件。

```xgo
// get.yap
html `<html><body>Hello, YAP!</body></html>`
```

#### gox.mod

```text
xgo 1.7

project main.yap AppV2 github.com/goplus/yap

class *.yap Handler
```

#### 自定义 Main 签名

`iHandlerProto` 的声明如下。

```go
type iHandlerProto interface {
    Main(ctx *Context)
}
```

编译器为每个处理程序生成带有 `*Context` 参数的 `Main`，因此处理程序可以直接访问 HTTP 请求和响应。与 cobra 一样，若 `yap.Handler` 实现了 `Main`，编译器会自动调用基类型的方法。

#### 模板接收者方法

```go
func XGot_AppV2_Main(app AppType, handlers ...iHandlerProto)
```

### MCP 服务器框架

`github.com/goplus/mcp`

MCP 框架定义了**多种独立的工作类**。

#### gox.mod

```text
xgo 1.7

project *_mcp.gox MCPApp github.com/goplus/mcp/server

class *_res.gox    ResourceApp ResourceProto
class *_tool.gox   ToolApp     ToolProto
class *_prompt.gox PromptApp   PromptProto
```

| 文件后缀 | 基类型 | 协议 |
| --- | --- | --- |
| `*_res.gox` | `server.ResourceApp` | `ResourceProto` |
| `*_tool.gox` | `server.ToolApp` | `ToolProto` |
| `*_prompt.gox` | `server.PromptApp` | `PromptProto` |

#### 项目结构示例

```files
project/
├── MyServer_mcp.gox
├── Files_res.gox
├── Search_tool.gox
├── Summarize_tool.gox
└── Greet_prompt.gox
```

`MyServer_mcp.gox` 是服务器入口。`Files_res.gox` 提供文件列表，`Search_tool.gox` 和 `Summarize_tool.gox` 定义工具，`Greet_prompt.gox` 定义问候模板。

#### 生成的 Go 代码（节选）

```xgo
// From myserver_mcp.gox — project class

type MyServer struct {
    server.MCPApp
}

func (this *MyServer) MainEntry() {
    ... // user code from myserver_mcp.gox
}

// Synthesized by the XGo compiler:
func (this *MyServer) Main() {
    filesRes      := new(Files)
    searchTool    := new(Search)
    summarizeTool := new(Summarize)
    greetPrompt   := new(Greet)

    server.Gopt_MCPApp_Main(this,
        []server.ResourceProto{filesRes},
        []server.ToolProto{searchTool, summarizeTool},
        []server.PromptProto{greetPrompt},
    )
}

// From search_tool.gox — work class

type Search struct {
    server.ToolApp
    *MyServer
}

func (this *Search) Main() {
    ... // user code from search_tool.gox
}

// Resources and prompts follow the same pattern with their respective base types.
```

#### 模板接收者方法

```go
func Gopt_MCPApp_Main(
    app       iAppProto,
    resources []ResourceProto,
    tools     []ToolProto,
    prompts   []PromptProto,
)
```

MCP 协议在运行时区分资源、工具和提示词，因此框架通过不同类型的切片接收这些实例。编译器按工作类声明的 `ProtocolType` 分组并传给相应的切片参数，随后框架将各组注册到 MCP 服务器。

## 内置单元测试框架

XGo 内置用来编写单元测试的类框架，文件后缀为 `_test.gox`。例如有以下函数。

```xgo
func foo(v int) int {
    return v * 2
}
```

可在 `foo_test.gox` 中直接测试此函数，无需声明 `TestXXX` 函数。

```xgo
if v := foo(50); v != 100 {
    t.error "foo(50) ret: ${v}"
}

t.run "foo -10", t => {
    if foo(-10) != -20 {
        t.fatal "foo(-10) != -20"
    }
}
```

## 常见需求与实现方式

| 需求 | 实现方式 |
| --- | --- |
| 将所有工作类实例放在同一组 | 在模板接收者方法中使用一个可变参数 |
| 运行时区分工作类种类 | 声明多条 `class` 指令，分别提供 `ProtocolType`，并为各组使用对应类型的切片参数 |
| 从项目类访问工作类实例 | 使用 `-embed` 选项 |
| 避免类型名冲突 | 使用 `-prefix=<P>` 选项 |
| 自定义 `Main` 或 `MainEntry` 的参数签名 | 在 `ProtocolType` 接口中声明所需签名 |
| 自动调用基类型入口方法 | 只要基类型实现了入口方法，编译器就会插入调用 |
