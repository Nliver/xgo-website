---
title: Link a local C function
description: Compile a C translation unit and call its exported function from Go.
---

Build a Go program that calls a local C function and prints `42`. You will use `LLGoFiles` to compile the C source and `//go:linkname` to tell LLGo which native symbol to call. Use LLGo `v1.0.10` and a working native toolchain. [Install LLGo](/docs/llgo/getting-started/installation)

## Create the module

In an empty directory, initialize the module and make a directory for the native source.

```sh
go mod init example.com/nativeadd
mkdir _wrap
```

The project will have three files.

```text
.
├── go.mod
├── main.go
└── _wrap/
    └── add.c
```

Save the Go program as `main.go`.

```go title="main.go" verify="manual"
package main

import (
	"fmt"
	_ "unsafe"
)

const LLGoFiles = "_wrap/add.c"

//go:linkname add C.add32
func add(a, b int32) int32

func main() {
	fmt.Println(add(19, 23))
}
```

Save the native implementation as `_wrap/add.c`.

```c title="_wrap/add.c" verify="manual"
#include <stdint.h>

int32_t add32(int32_t a, int32_t b) {
    return a + b;
}
```

The bodyless Go declaration refers to the `add32` symbol defined in `add.c`. The `C.` prefix selects the C calling convention. The C function takes two `int32_t` values and returns an `int32_t`, so the Go declaration uses `int32` for both parameters and the return value. Those types are part of the application binary interface (ABI), the rules the two languages follow to pass values at runtime. Go type checking cannot verify the C signature.

## Build and run

```sh
llgo build -o hello .
./hello
```

```text
42
```

LLGo resolves `LLGoFiles` paths relative to the package directory. The recommended `_wrap` directory keeps native source beside the Go package while Go tooling ignores it as a package directory. Separate multiple files with semicolons.

```go title="main.go" verify="manual"
const LLGoFiles = "_wrap/add.c;_wrap/format.c"
```

## Compile the wrapper as C++

In `main.go`, change the `LLGoFiles` value to `"_wrap/add.cpp"`. Save the following code as `_wrap/add.cpp` and leave the Go declaration as written.

```cpp title="_wrap/add.cpp" verify="manual"
#include <stdint.h>

namespace {
int32_t sum(int32_t a, int32_t b) {
    return a + b;
}
}

extern "C" int32_t add32(int32_t a, int32_t b) {
    return sum(a, b);
}
```

Run `llgo build -o hello .` and `./hello` again. The program still prints `42`. LLGo selects the compiler by filename extension. The C++ helper stays inside the source file, and `extern "C"` gives the public wrapper the symbol name that `C.add32` expects.

## Add a native dependency

Put options for compiling a wrapper before the colon in `LLGoFiles`. If the wrapper calls an external library, provide linker flags separately. LLGo’s own libffi binding uses `LLGoFiles` for header search paths and `LLGoPackage` for the link options. [Upstream libffi configuration](https://github.com/xgo-dev/llgo/blob/v1.0.10/runtime/internal/clite/ffi/link_flags_default.go)

```go title="main.go" verify="manual"
const (
	LLGoPackage = "link: $(pkg-config --libs libffi); -lffi"
	LLGoFiles   = "$(pkg-config --cflags libffi): _wrap/libffi.c"
)
```

The `LLGoFiles` flags can use literal options or a whitelisted `$(pkg-config ...)` or `$(llvm-config ...)` substitution. In the `LLGoPackage` declaration above, LLGo uses the options from `pkg-config --libs libffi` when the command returns flags and falls back to `-lffi` otherwise.

## Troubleshoot the build

- For a missing header, check the wrapper's include paths. If it uses libffi, run `pkg-config --cflags libffi` to see which compile options the installed package supplies.
- For an undefined symbol, run `llgo build -x -o hello .` to see the build commands. Check that `LLGoFiles` lists the file that defines the symbol, that a C++ wrapper uses `extern "C"`, and that any required external library appears in the link command.
- For an architecture mismatch, run `llgo env GOOS GOARCH` and compare the target with the architecture of the selected native library. On macOS or Linux, `file` can identify the architecture of a library or executable.
- If the binary links but returns an unexpected result, compare the Go declaration against the native definition, including parameter widths, signedness, return type, and calling convention.

See how to select native sources with build constraints and how to bind pointers, structs, callbacks, or variables. [LLGoFiles](/docs/llgo/native-files) · [Calling conventions](/docs/llgo/reference/calling-conventions)

If the library already provides a Go package that declares the native calls, start with that package. [Use LLGo bindings](/docs/llgo/tutorials/bindings)
